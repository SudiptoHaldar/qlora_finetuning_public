# QLoRA Finetuning: Claude Code Guidelines

Project package name: `qlora_finetuning` (source of truth: `.claude/key_value.md`).

## 🔄 Project Awareness & Context
- **Always read `reqspecs/0. PLANNING/high_level_plan.md`** at the start of a new conversation to understand the project's architecture, goals, style, and constraints.
- **Check the active spec group's roadmap** (`reqspecs/reqs/req_NNN_*/req_NNN_roadmap.md`) before starting a new task — it is the single source of truth for the version sequence and each version's status.
- **Use consistent naming conventions, file structure, and architecture patterns** as described in `reqspecs/0. PLANNING/high_level_plan.md` and the req_000 roadmap.
- **Use the repo venv** (`venv/` at repo root) for every Python command, including unit tests, without activating it: `venv\Scripts\python -m <tool>` on Windows (for example `venv\Scripts\python -m pytest -q`), `venv/bin/python -m <tool>` on POSIX.
- **Update requirements.txt** with python libraries to be installed/imported (plain PyPI pins — no CUDA index URLs; the CUDA build of torch and the training stack go in `requirements-train.txt`, req_000 v0.03).
- **Check `reqspecs/references/`** before fetching documentation from the web: `common/gotchas.md`, `common/troubleshooting.md`, and `tech/<technology>.md`.

## 🧱 Code Structure & Modularity
- **Organize files for readability and separation of concerns, not by line count.** A module holds one concern and can be as long as that concern needs. Split a file when it holds concerns that can be understood, tested, or changed apart; never split one only because it is long (owner's decision, 2026-11-16).
- **Organize code into clearly separated modules**, grouped by component under the `qlora_finetuning` parent package:
    - `qlora_finetuning/tracking/` - Run registry and cost ledger
    - `qlora_finetuning/data/` - FinQA snapshot, split manifest, serialization, token budget
    - `qlora_finetuning/dsl/` - Program parser and safe executor
    - `qlora_finetuning/evaluation/` - Metrics, Predictor protocol, evaluation runner
    - `qlora_finetuning/local_qlora/` - Path A: 4-bit inference backend, QLoRA training, SageMaker launcher
    - `qlora_finetuning/frontier/` - Path B: Bedrock adapter, JSONL export, job control
    - `qlora_finetuning/comparison/` - Configuration freeze, test unlock, the gate on a test run, the six-arm record; the cost model (`cost`, `cost_scenarios`, `cost_bill`, `cost_report`, `cost_config`); the comparison report (`statistics`, `outcomes`, `report_record`, `report_tables`, `report_build`, `report_examples`, `report_config`, and the module that draws its SVG figure)
    - `qlora_finetuning/demo/` - CLI: context + question -> program -> executed answer
    - `qlora_finetuning/packaging/` - The adapter package, the merged copy, their model cards, and the package record
    - `qlora_finetuning/public_export/` - The public copy of the repository: a commit's files, redacted, with a snapshot notice
    - `scripts/` - Operator entry points (`aws_check`, `env_check`, `finqa_fetch`, `finqa_report`, `finqa_split`, `finqa_serialize`, `finqa_tokens`, `finqa_gold_check`, `evaluate`, `nova_baseline`, `nova_export`, `nova_tune`, `nova_tuned`, `qlora_train`, `job_run`, `sagemaker_job`, `qlora_select`, `qlora_analyze`, `qlora_iterate`, `qlora_local`, `comparison_freeze`, `comparison_runs`, `comparison_cost`, `comparison_report`, `ledger_summary`), run as modules from the repo root: `venv\Scripts\python -m scripts.<name>`
    - `config/` - Versioned YAML (split, prompt, token budget, DSL limits, evaluation allowances, training, AWS, Path A loading and decoding in `local_qlora.yaml`, Path A's jobs in `sagemaker.yaml`, Path B settings in `frontier.yaml`, prices in `pricing.yaml`, the six arms and the freeze files in `comparison.yaml`, the cost model's scenarios in `cost_model.yaml`, the report's statistics and pairs in `report.yaml`, its deviations list in `report_deviations.yaml`)
- **Use clear, consistent imports** (absolute `qlora_finetuning.*` imports).
- **Use `qlora_finetuning/settings.py`** for configuration: env vars via its dotenv-backed accessors (`get_str`/`get_int`), tunable parameters via `load_config()` from versioned YAML under `config/` — never hard-code tunable numbers (hyperparameters, tolerances, seeds, instance types, prices). Config files are `config/<name>.yaml` with an integer `version:` key; `load_config("<name>", required=[...])` raises `ConfigError` naming every missing key.
- **Use `qlora_finetuning/logging_setup.py`** for logging: call `setup_logging()` once in an entry point and `get_logger(__name__)` in modules. Log lines go to standard error; a script's results go to standard output.
- **Keep lint clean** under `ruff.toml` (line length 100): `venv\Scripts\python -m ruff check .`. CI runs the same lint and tests on every pull request to `main`.
- **Provide Usage Example** using examples provided in the feature; use sample values if no specific examples have been provided.
- **Track every run**: a training or evaluation entry point does its work inside `with start_run(...)` from `qlora_finetuning.tracking` and records what it consumed with `run.record(...)`, naming where each number came from (`measured`, `aws_api`, `computed`, `bill`). Record quantities, never dollars. See `reqspecs/references/project_patterns/run_tracking.md`.
- **Get FinQA examples with `load_split("fit" | "dev" | "quick_dev")`** from `qlora_finetuning.data`, never from the Hub, a file path, or `load_raw_examples`: the loader checks the pinned checksums and the frozen split manifest on every load. Only code inside `qlora_finetuning/data/` and the three data scripts that a guard test lists may use the raw reader. See `reqspecs/references/project_patterns/split_loading.md`.
- **The test split is locked**: `load_split("test")` raises `TestLockedError` until the owner unlocks it (req_005 v5.01). Never catch that error or work around it, never create or edit `splits/test_unlock.json` (only `venv\Scripts\python -m scripts.comparison_freeze unlock --yes --freeze <hash>` writes it, and only the owner runs that, once), and never change `config/split.yaml` or the manifest: the split is frozen. Choose prompts, checkpoints, and settings on dev only.
- **After the unlock the gate protects the test split** (`check_test_run` in `qlora_finetuning/comparison/gate.py`; `run_evaluation` calls it for every run on `test`, so nothing goes round it). A test run is allowed only for the six arms of `config/comparison.yaml`, at the predictor name, model id, and settings of the freeze record (`splits/config_freeze.json`), with `--scope measured`, without `--limit`, a Qwen arm inside a SageMaker job and a Nova arm against Bedrock, and **once per arm**: an interrupted run is resumed, a second run is refused. Only the owner voids a run (`scripts.comparison_runs void`, with a written reason, for a pipeline or service fault and never for disappointing answers). The `gold` predictor may run on test as a free check. An agent never starts a test run and never looks at test replies; it runs `comparison_freeze check` and `status`, `comparison_runs status`, and `sagemaker_job plan`.
- **Nothing frozen changes after the freeze**: `config/prompt.yaml`, `split.yaml`, `data.yaml`, `token_budget.yaml`, `dsl.yaml`, `evaluation.yaml`, the gold flags, each arm's predictor settings (`config/local_qlora.yaml` inference and quantization values, `config/frontier.yaml` `models` and `inference`), the selection record, and the tuning record's deployments. A value that decides no reply may still be added elsewhere (a price, a pacing rate). `comparison_freeze status` lists what changed; a test of the suite fails on a changed value once a freeze record is committed. Hashes of text files are taken with Unix line ends (`file_sha256`), because git checks them out with CRLF here and a job has LF.
- **Later versions take the six test runs from `reports/comparison/six_arm_test_runs.json`** (written by `scripts.comparison_runs record` after checks C1 to C8), never by arm name or by searching the ledger. `qlora_finetuning/comparison/` may import `local_qlora/` and `frontier/`, but imports no boto3 module at module level; `gate.py` imports neither, nor the runner.
- **Every dollar figure comes from the cost model** (req_005 v5.02): `scripts.comparison_cost report` writes `reports/comparison/cost_model.json`, and later versions take costs from that file and compute none themselves. A figure is a ledger quantity times a price from `config/pricing.yaml`, as `Decimal`, or a billed amount as it stands. Each effective ledger record is in exactly one category (train, select, test, development, no charge); a new kind of record needs a branch in `cost.place` and a test. Pattern: `reqspecs/references/project_patterns/pricing_a_ledger_record.md`.
- **The comparison report is built, never edited** (req_005 v5.03): `scripts.comparison_report build` writes `reports/comparison_report.md`, `reports/comparison/comparison_statistics.json` and `.md`, the SVG figure, and the block between the markers in `README.md`, after checks R1 to R8. Wording lives in `qlora_finetuning/comparison/report_template.md`, where every figure is a `{{placeholder}}` filled by `report_tables.placeholders`; a deviation is an entry in `config/report_deviations.yaml`. **Every interval and p-value comes from `comparison/statistics.py`** (`bootstrap_rates`, `interval`, `mcnemar_exact`, `holm`), through `report_record.build_statistics`; a difference is called settled only when its adjusted p-value and both intervals (by example and by company) say so. Per-example results come from `outcomes.read_arms`, which rescores stored replies and holds no text. These modules may read test rows on this machine (the execution plan's principle 6, as amended); they ask no model and upload nothing. A written file names models by arm, never by a deployment ARN, and holds counts and example ids only; example text is written by `report_examples` under git-ignored `artifacts/` and nowhere else. No plotting or statistics library is added: the figure is SVG text written by the project's own code. Pattern: `reqspecs/references/project_patterns/paired_comparison.md`.
- **Record the split in every run**: pass `split_manifest_hash=manifest_hash()` to `start_run`.
- **Never truncate a prompt or a target.** The training length (`max_length`) and the reply limit (`max_new_tokens`) come from `config/token_budget.yaml` through `load_token_budget_config()`; the base model and its tokenizer are loaded at the commit pinned there. A record longer than `max_length` is an error that names the example, never something to cut.
- **Prompts come from the serializer**: get the system, user, and target texts from `serialize_split(...)` or `build_record(...)` in `qlora_finetuning.data`, and wrap them without changing a character. No prompt wording is written in code; it lives in `config/prompt.yaml`, and every run records the prompt id. Once any arm has been run on a wording, changing it means a new `version` there and a rerun of every arm. See `reqspecs/references/project_patterns/canonical_record.md`.
- **Read and run a model's reply only through `qlora_finetuning.dsl`**: `run_reply(text, table)` returns the executed value or a named error code and never raises on any string. No other code parses reply text, and no reply text is ever passed to `eval`, `exec`, `compile`, or `ast.literal_eval`. Store the outcome's `error_code`, `deviations`, and `notes` with every prediction; do not round or compare values outside the metrics. See `reqspecs/references/project_patterns/reply_scoring.md`.
- **Score only through `qlora_finetuning.evaluation`**: `score_reply(outcome, gold, config)` for one reply and `summarize(scores, flagged=load_gold_flags())` for totals. The allowances come from `config/evaluation.yaml` through `load_evaluation_config()`; no tolerance, rounding, or comparison is written anywhere else, and no rate is computed by hand. They were fixed before any model was scored: changing one means rescoring every arm and rebuilding the gold flags with `venv\Scripts\python -m scripts.finqa_gold_check`. Report the total over all examples as the headline, with the unflagged total beside it; never drop an example from a denominator.
- **Evaluate a model only through `run_evaluation`** (`qlora_finetuning.evaluation.runner`, or `venv\Scripts\python -m scripts.evaluate`). A backend implements the `Predictor` protocol and nothing of the loop: no code of its own walks a split, writes a predictions file, or adds up an accuracy. A predictor that cannot answer raises `PredictorError`; it never returns an empty reply in place of a failure. Quote a number only from a run whose summary says `result: true`. Predictions stay under git-ignored `artifacts/runs/`; counts go to the committed `ledger/`. Import the runner by its own module name: it is not exported from `qlora_finetuning.evaluation`. See `reqspecs/references/project_patterns/evaluation_run.md`.
- **Never commit dataset text**: any example may be a test example, so a committed file (report, fixture, test, document) may hold FinQA counts and example ids, never question, passage, table, or answer text. Tests use invented rows from `tests/data/synthetic.py`.
- **Keep secrets and personal details out of the repo**: AWS credentials stay in the AWS CLI profile, other secrets in `.env` (git-ignored); no access key, token, or email address goes into a committed file.
- **Call Bedrock only through `BedrockProvider`** (`qlora_finetuning/frontier/bedrock.py`), the one module that calls a model. It sends the canonical system and user texts unchanged with the decoding values of `config/frontier.yaml` and nothing else; a setting that can change a reply goes into that file and into the predictor's `settings`, never into code. Every call is billed, so a run that reaches Bedrock is started by the owner; tests give the provider a stub client or the predictor a stub provider. A hosted backend's token counts are the service's own (`usage_source = "aws_api"`), never an estimate. See `reqspecs/references/tech/bedrock_nova.md`.
- **Make Bedrock training files only with `export_files`** (`qlora_finetuning/frontier/export.py`, or `venv\Scripts\python -m scripts.nova_export`). It exports `fit` and `dev` and takes no split name; every record is exported, repeated ones included, so both paths train on the same examples; a file is never edited by hand. Check files with `validate_export`, which reads them back from disk. The files hold dataset text and stay under git-ignored `artifacts/bedrock/`; only hashes, counts, and dollars go into the committed gate record. `staging.py` is the only code that writes to S3 for Path B: the owner runs it (`--upload`).
- **Start, stop, deploy, and delete on Bedrock only through `BedrockTuning`** (`qlora_finetuning/frontier/tuning.py`, or `venv\Scripts\python -m scripts.nova_tune`). A launch runs checks T1 to T9 and refuses if one fails; a job is created with a request token derived from the model, the files, the hyperparameters, and the attempt, and a job that already exists with that token is adopted, never created twice. The tuning record (`reports/frontier/nova_tuning.json`, read with `read_tuning_record()`) is written the moment a job ARN is known and is committed; it is where later code finds a deployment ARN. `launch`, `deploy`, `stop`, and `teardown` change AWS: the owner runs them, with `--yes`; an agent runs `plan` and `status` only. No command launches more than the one model it is told to, and nothing launches because something else finished. **Never create Provisioned Throughput**: no code may call it (a guard test scans for it), and a launch or deploy is refused while the account has any. A job's cost enters the ledger as estimated tokens (`computed`) and is replaced by the billed amount (`bill`) that the owner reads from the AWS bill. Only `bedrock.py`, `staging.py`, and `tuning.py` import boto3 or botocore.
- **Ask the Qwen model only through `QwenBackend`** (`qlora_finetuning/local_qlora/backend.py`, built by `load_backend`; from the command line `venv\Scripts\python -m scripts.evaluate --predictor qwen3-4b`). It is the only module under `local_qlora/` that imports the training stack, and only inside functions. It loads the model and commit pinned in `config/token_budget.yaml` from the local cache (`local_files_only=True`: a run never downloads), in 4-bit, with the values of `config/local_qlora.yaml`. Prompts are wrapped by `render_chat` (`local_qlora/render.py`) with thinking off and are never truncated. Decoding is greedy and stops at the model's own end tokens or the reply limit: no stop string, no cut after the `ANSWER` line, no sampling, and no wording for Qwen alone. The batch size is part of a run's settings, because a reply can depend on its batch. Everything that can fail before the first reply (no stack, no GPU, weights not downloaded, a changed tokenizer) is a `ConfigError` in the factory, before a run exists. A backend's own figures (peak GPU memory, speed) reach the run through the predictor's `measurements()` method. Local runs are free and are development evidence only: no local number goes into the comparison. See `reqspecs/references/tech/hf_training_stack.md`.
- **Train the Qwen adapter only through `run_training`** (`qlora_finetuning/local_qlora/training.py`, or `venv\Scripts\python -m scripts.qlora_train`). It encodes records with `encode_records` (`local_qlora/render.py`): the inference prompt, the target, the end token, labels on the reply only, and the length the token budget counted. **Nothing is truncated**: a record over `max_length` is a `LengthError` before the model loads, and the trainer is given `max_length=None` because its own default cuts rows silently. Every hyperparameter comes from `config/training.yaml` and is passed explicitly (`trainer_arguments`); none is written in code or left to a library default. A run probes its worst batch first, records one ledger line (time, records, training tokens), and keeps every checkpoint. Resuming is a new run (`--resume`), refused under other settings. Only `backend.py` and `training.py` import the training stack under `local_qlora/`. Training reads `fit`, and `dev` for a loss figure only; a checkpoint is chosen by dev execution accuracy, never by loss, and is scored after training through the runner. Run `qlora_train --smoke` after any change to the stack, the config, or the pipeline. A full run is hours of GPU time: do not start one unasked.
- **Name an adapter by its training run**, `RUN_ID` or `RUN_ID/checkpoint-N`, never by a path: `scripts.evaluate --predictor qwen3-4b-tuned --adapter ...`, built by `build_tuned_predictor`. It refuses an adapter trained for another model commit, prompt wording, or split (`check_adapter`, from the adapter's metadata). A smoke adapter is never arm A1's result: its predictor is named `qwen3-4b-tuned-smoke`. Adapters and checkpoints stay under git-ignored `artifacts/`.
- **Run Path A in AWS only through `SageMakerJobs`** (`qlora_finetuning/local_qlora/sagemaker.py`, or `venv\Scripts\python -m scripts.sagemaker_job`). `launch` and `stop` change AWS and are billed: **the owner runs them, with `--yes`**; an agent runs `bundle`, `rehearse`, `plan`, `status`, `logs`, and `pull`, which create nothing in AWS. A launch runs checks J1 to J11 and refuses if one fails (J11: a job on the test split is one the freeze and the unlock allow; J10: once a checkpoint is selected, a full training run is the one registered corrective iteration; J9: a `train`, `score`, or `evaluate` job must have an estimate, computed by `local_qlora/estimate.py` from what a pulled job measured, that fits in its limit); `keep` also writes to S3 and is the owner's; a job that exists under the name is adopted, never created twice; the job record (`reports/local_qlora/sagemaker_jobs.json`, read with `read_job_record`) is written the moment a job's ARN is known and is committed. A job runs a commit (`git archive`; a dirty tree is refused), never a working tree. Every job has a maximum runtime from `config/sagemaker.yaml`, and the Path A cap there is checked against billable seconds times the price of `config/pricing.yaml`. The ledger gets billable seconds from `DescribeTrainingJob` (`aws_api`), never dollars. A job executes `scripts.job_run`, which calls `run_training` and `run_evaluation` unchanged: write no training or evaluation logic for the cloud alone. Rehearse a changed task locally (`rehearse`) before it is launched. Jobs are created with plain boto3: no `sagemaker` SDK, no Docker. AWS sessions and the sign-in message come from `qlora_finetuning/aws_common.py`, which both paths share; `local_qlora/` and `frontier/` still do not import each other. See `reqspecs/references/tech/sagemaker.md`.
- **Say why replies were wrong only through `classify`** (`qlora_finetuning/evaluation/failures.py`: `run_failures`, `count_failures`; req_003 v3.05). A category is computed from the stored predictions line and the gold program, never assigned by reading, and is the same for every arm; the module imports neither `local_qlora/` nor `frontier/`. Path A's report is `analyze_run` (`local_qlora/analysis.py`, or `venv\Scripts\python -m scripts.qlora_analyze --run <run>`), which writes `reports/local_qlora/error_analysis.json` and `.md`: counts and example ids. **No committed file holds a reply or a gold program**; `--show` prints them to the terminal only.
- **A training run made on this machine is never an arm** (req_003 v3.06). It is recorded `where: local`, `scope: dev`; never pass `--scope measured` here. Its record is the local note (`local_note` in `qlora_finetuning/local_qlora/local_note.py`, or `venv\Scripts\python -m scripts.qlora_local note --run <run>`), a file of its own that no code reads as a selection: not `--adapter selected`, not `keep`, nothing of `comparison/`. Put no price on a local run. Everything printed or written about one carries `LABEL` (`local_qlora/local_run.py`). Read the machine only through that module's probes (`probe_gpu`, `probe_power`), which answer "unknown" and never raise, and pass stand-ins for them in tests. An agent runs `qlora_local preflight`, `status`, and `note`; **the hours-long `qlora_train` without a flag is started by the owner**.
- **A second full training run of Path A exists only as the one registered corrective iteration** (req_003 v3.05), and only after a `missed` verdict. The owner edits one value of `config/training.yaml`; `propose` (`local_qlora/iteration.py`, or `scripts.qlora_iterate propose`) checks I1 to I5 and writes `reports/local_qlora/iteration.json` before anything is paid for. The variables are `ITERATION_VARIABLES` in `training_config.py`; `lora.alpha` follows `lora.r`. Never change, inside Path A, a setting the arms share: the prompt, the split, the serialization, the reply limit, the inference settings, the evaluation allowances. The analysis reports a finding; code never chooses the change. `select_checkpoint` compares a second run with the selected checkpoint by the same rule (a tie keeps the first) and writes schema 2; read either schema with `read_selection`. `config/training.yaml` must end as the selected run's settings (`iteration_status`).
- **Arm A1 is the checkpoint the selection record names, and nothing else** (req_003 v3.04). `select_checkpoint` (`qlora_finetuning/local_qlora/selection.py`, or `venv\Scripts\python -m scripts.qlora_select --run <training run>`) chooses by execution accuracy on dev, never by loss, runs checks L1 to L6, and writes `reports/local_qlora/adapter_selection.json` and `.md`, which are committed and hold counts, ids, hashes, and amounts: no reply, no example text, no time stamp. Ten runs carry arm A1, so never pick a run by its arm: pass `--adapter selected`, or call `selected_adapter` / `read_selection` (`local_qlora/adapters.py`). Only runs made in SageMaker with `--scope measured`, in pulled jobs, can be selected; a local or smoke run can only be rehearsed with `--check`. The thresholds are in `config/training.yaml` (`selection`); a `missed` verdict starts nothing. Score checkpoints only through the `score` task (`run_task("score", run=...)`), which reuses complete runs and resumes cut-short ones through `find_evaluation` (`local_qlora/scoring.py`): write no second loop over checkpoints.
- **A job is given a data bundle, never the snapshot**: `export_bundle` (`qlora_finetuning/data/bundle.py`, or `sagemaker_job bundle`) writes `fit` and `dev`. The only other bundle is the **test bundle** (`sagemaker_job bundle --split test`, req_005 v5.01): the test examples alone, writable only after the unlock, given only to an `evaluate` job with `--split test`, and uploaded by the owner's launch. That is the one upload of test rows to S3. A bundle never mixes test rows with training rows; from a `fit` and `dev` bundle `load_split("test")` is refused whatever the unlock record says. A launch on the test split must pass check J11 (the gate, asked at plan time), and `rehearse` refuses `--split test`. `serialize_split("test")`, `export_files`, `run_training`, the `score` task, and `qlora_select` never read test rows, locked or unlocked. A bundle holds dataset text: it stays under git-ignored `artifacts/` and in the private bucket.
- **Ask a tuned Nova model only through the tuned predictors** (`nova-lite-tuned`, `nova-pro-tuned` in `scripts.evaluate`, built by `build_tuned_predictor` in `qlora_finetuning/frontier/predictor.py`). They take the deployment from the tuning record's latest attempt (`tuned_attempt()` in `qlora_finetuning/frontier/tuned.py`), refuse unless the job completed, the deployment is Active (recorded, and confirmed by one read from Bedrock), and the model was tuned on the current export, and send the untuned request with only the `modelId` changed. Never paste a deployment ARN into config or code. A predictor that is called under one id and billed under another sets `usage_model_id` to the billed one: the ledger records usage under an id that `config/pricing.yaml` can price. Tuned runs are billed, so the owner starts them. Compare tuned with untuned only through `scripts.nova_tuned`, which pairs runs and refuses unless prompt, split, settings, and example order are equal; the thresholds of its verdict are in `config/frontier.yaml` (`tuned_evaluation`), and a missed verdict starts nothing.
- **No fine-tuning job without a passing gate record**: code that starts a job reads `read_gate_record()` (`qlora_finetuning/frontier/training_estimate.py`) and refuses unless it says `passed`, the configured epoch count is the one it priced, and the objects in S3 have the recorded SHA-256. The gate never passes on an assumed token ratio.
- **Take prices only from `config/pricing.yaml`** through `qlora_finetuning.frontier.pricing` (`load_pricing`, `inference_cost`). A price is quoted text read as `Decimal` and carries the date of its AWS price list; no price is written in code, and no dollar amount is stored in the ledger.
- **The demo shows, it does not measure** (`qlora_finetuning/demo/`, `venv\Scripts\python -m qlora_finetuning.demo`; req_006 v6.01). `answer(predictor, demo_input)` takes the prompt from `load_prompt()` and `format_user(...)`, asks any `Predictor` with one request, gives the reply to `run_reply`, and compares the model's answer with its own program's result through `answer_agrees` in `evaluation/metrics.py` (not a metric: no run summary reports it). The demo answers with Qwen only, by adapter name (`selected` by default, never a path; `resolve_tuned_adapter` is the check without the load). It takes no split name and no example id, reads no dataset row, starts no run, writes no file, imports no boto3, `frontier`, `comparison`, or runner module, and prints ASCII and unrounded values; guard tests in `tests/demo/test_guards.py` enforce this. Input is a JSON file somebody wrote (`load_input`); the committed sample is invented, and no FinQA row is ever given to the demo. Its output is never evidence: nothing it prints goes into a report.
- **Build a package only through `scripts.hf_package`** (`qlora_finetuning/packaging/`; req_006 v6.02). The adapter package is built from the checkpoint the selection record names, after its hash is checked (`selected_source`): never from `artifacts/adapters/<run>/`, which holds a run's last step, another adapter. Its two adapter files are copied byte for byte and never edited. The merged copy (`merge.merge_adapter`, the only module of `packaging/` that imports the training stack) is made from the full-precision base model and saved with greedy generation settings; **it is not arm A1**, it is scored on dev only, and it is withheld when it has `noise_examples` or more examples fewer right than the adapter. A package is scored only through `run_evaluation`, by the predictors `qwen3-4b-package`, `qwen3-4b-merged`, and `qwen3-4b-merged-full` (`packaging/predictors.py`), which are no arms, are refused on test, and whose runs are local, free, and carry no price. **A model card is built, never edited**: its wording is a template beside `packaging/cards.py`, every figure a `{{placeholder}}` filled from the committed records, and the code it prints is the code `hf_package verify` executed in an empty directory. A card is written only when every licence entry of `config/packaging.yaml` is confirmed by the owner. A package, a card, and the package record hold no dataset text, account number, ARN, S3 path, job name, machine path, or email address (`packaging/scan.py`, check P5). Nothing in `packaging/` uploads anything: publishing is the owner's step (req_006 v6.03). Pattern: `reqspecs/references/project_patterns/release_package.md`.
- **Publish a package only through `scripts.hf_publish`** (`packaging/publish.py`, and `packaging/hub.py`, the one module that talks to the Hugging Face Hub; req_006 v6.03). Only the folders `hf_package` built are uploaded, each to a private repository, after every file on disk has the size and hash of the package record; a repository that holds anything else is refused. **`upload` is the owner's, with `--yes`**; an agent runs `plan`, and `check` once the repositories are public. The token is read from `HF_TOKEN` in the environment or `.env`: never a command-line argument, never printed, never logged, never in a record; everything printed passes through `redact`. No code makes a repository public, deletes one, or edits a file on the Hub (a guard test scans for those calls): that is the owner's, on the website. A card is never edited on the Hub; change the template, build with `hf_package cards`, upload again.
- **The public repository is made only by `scripts.public_export`** (`qlora_finetuning/public_export/`; req_006 v6.04), and is never edited by hand: a change is made here, committed, and exported again. An export is of a commit (`git archive`), never of the working folder, and `build` refuses while tracked files have uncommitted changes. What is left out, replaced, or rewritten is listed in `config/public_export.yaml`; a replacement is literal and counted, and the AWS account number to replace is read from `config/aws.yaml`, never written a second time. **A new file that holds something private gets a rule there before it is committed.** The tool writes into an empty folder or over a previous export, removes only what the previous export wrote, and never touches that folder's `.git`. It makes no commit there, no push, and no network call: **committing in the public folder, pushing, and making the repository public are the owner's**. A test that verifies the committed freeze records against the real repository carries `@pytest.mark.private_records`; it runs here and is skipped where `PUBLIC_SNAPSHOT.md` exists. Give that marker only to a test that fails in a copy because a freeze record was redacted, never to quiet a failure. A test that plants a private-looking value writes it in pieces, or the value is listed under `invented_values`, so the scan of the copy does not find it. Pattern: `reqspecs/references/project_patterns/release_package.md`.
- **Log every AWS command** that is run in `administration/aws_commands_run.md` with a plain-English description. Anything that creates, changes, or deletes an AWS resource, or that is billed, is run by the owner; read-only checks may be run by Claude.

## 🧪 Testing & Reliability
- **Always create Pytest unit tests for new features** (functions, classes, scripts, etc).
- **After updating any logic**, check whether existing unit tests need to be updated. If so, do it.
- **Tests live in `/tests`**, mirroring the `qlora_finetuning` package structure (tests for `scripts/` live in `tests/scripts/`).
  - Include at least:
    - 1 test for expected use
    - 1 edge case
    - 1 failure case
- **Tests must not need a GPU, the network, credentials, or a paid call**: such checks go behind `@pytest.mark.gpu`, `@pytest.mark.network`, or `@pytest.mark.paid` and are deselected by default in `pytest.ini`. Run them on purpose, for example `venv\Scripts\python -m pytest -m network -q`. All three are registered in `pytest.ini`; an unregistered marker is an error.
- **Pass external clients into functions** (boto3 clients, model backends) so a test can hand over a stub.
- **Never import the training stack at module level** (`torch`, `transformers`, `datasets`, `peft`, `trl`, `accelerate`, `bitsandbytes`, `tokenizers`, `safetensors`, `huggingface_hub`). Import it inside the function that needs it. CI does not install `requirements-train.txt`, so every module and every test file must load without it; a guard test enforces this. A test that needs the real libraries is marked `gpu`.

## ✅ Task Completion
- **A version is ✅ Complete when it passes locally**: `venv\Scripts\python -m pytest -q` and `venv\Scripts\python -m ruff check .` are green on the owner's machine, the PRP's own acceptance checks pass, and the work is committed. A pull request and its CI run are **not** needed to mark a version complete (owner's decision, 2026-11-15: opening and merging a pull request per version costs too much time). CI still runs whenever a pull request to `main` is opened, which the owner does when convenient, typically for several versions at once; a CI failure found then is fixed as a follow-up and noted in the roadmap. Do not mark a version 🟡 only because CI has not run.
- **Update the spec group's roadmap immediately** when a version's status changes (spec written, PRP authored, implementation shipped) — quick-reference table row, detail section, version log, and the "Last updated" header line, all in the same turn.
- Add newly discovered sub-tasks or TODOs to the roadmap (open questions in the relevant version's detail section, or a version-log entry) rather than a separate task file.
