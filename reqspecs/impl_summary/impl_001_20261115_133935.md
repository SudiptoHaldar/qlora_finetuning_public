## What was implemented

- **Prompt definition.** `config/prompt.yaml` holds the system text and the layout of the user
  and target texts, with a version. Its prompt id is a SHA-256 of the parsed values, so a
  comment or key order does not change it and any character of the wording does. A test pins
  the id.
- **Serializer.** `build_record(example, prompt)` returns a `CanonicalRecord`: the system
  text; a user text of text evidence in document order (or `(none)`), the whole table as
  Markdown with cells word for word, and the question; and a two-line target with the
  dataset's program unchanged and `exe_ans` as the answer, scientific notation written out
  through decimal arithmetic. `serialize_split(name)` goes through `load_split`, so the test
  lock applies. `format_user` and `format_target` serve input that is not a dataset example.
- **Report.** Lengths in characters, counts, skipped evidence keys, and a digest per split,
  with checks C1 to C10. It holds no example text. C9 compares with the digests in the
  committed report and fails once, loudly, when the records change.
- **Script.** `python -m scripts.finqa_serialize`, with `--check`, `--dump` (records to
  git-ignored `artifacts/serialized/`), and `--show "<id>"` (one fit or dev record to the
  terminal; a test id is refused before any data is read).
- **One layout in the repository.** The hand-written smoke example in `scripts/env_check.py`
  is replaced by one built with `format_user` and `format_target`.

## Differences from the spec and the PRP

- **C9 has no "first build" wording.** Its passing detail lists the digests, so the report is
  identical whether or not a committed report existed.
- **Quick-dev is reported but not checked separately**, since its records are dev records.
- **`--check` cannot be combined with `--dump`**, because `--check` promises to write nothing.
- **The plan's example reply changed** from `multiply(#1, 100)` / `8.4%` to the form the data
  actually has: the result of the program, `0.08402`.

## Found and fixed on the way: a defect in the v0.04 run registry

A tracking test had failed once in each of the last three sessions and passed on rerun. It was
reproduced and identified: `os.replace` in `tracking/registry.py` is refused by Windows with
"Access is denied" when another program briefly holds a manifest that was just written, which
happens when a run is finished immediately after it starts. It failed in 3 of 25 runs of the
tracking tests. In a real run it would have lost the run's final status.

`_write_json` now tries the replace up to eight times with a short, growing wait; any other
error is raised at once. Three tests cover it. After the fix: 0 failures in 40 runs. This is
outside v1.03's scope and is recorded in the req_000 roadmap.
