## What was implemented

- **Reply parser.** `parse_reply` finds the program and the answer by the labels of
  `config/prompt.yaml`. A reply is strict when it holds exactly the two fields; otherwise it
  is still read when it has a program line, and the broken rules are named (`text_before`,
  `text_between`, `text_after`, `label_case`, `answer_missing`).
- **Program parser.** `parse_program` reads the text once, by hand: ten operation names, two
  arguments per step, the number forms the dataset uses, seventeen constants, references to
  earlier steps only. A table step's row name runs to the last comma outside inner brackets,
  so names with brackets and commas work. `format_program` gives the canonical form.
- **Executor.** `execute` runs the steps on floats and does not round. Table operations find
  a row by its exact name (the last one when repeated, with a note), read its cells with one
  rule, and fail by name on a row that is not all numbers.
- **One call.** `run_reply(text, table)` joins the three and returns a `ReplyOutcome` for any
  string: value, canonical program, strict flag, deviations, notes, or an error code with its
  stage.
- **Errors.** Nineteen codes in three stages. Messages quote at most 40 characters, in ASCII.
- **Safety.** No `eval`, `exec`, `compile`, `literal_eval`, or `__import__`; a test scans the
  package source for them and for imports beyond a short allowed list.

## Differences from the spec and the PRP

- **A table cell may carry a plus sign.** The hand check found 18 cells of the form `+5%`,
  all in one table, that the trial rule read and the first built rule did not. The cell rule
  now accepts a leading plus; a program literal still may not have one. No gold program names
  those rows.
- **Blank lines and leading spaces do not break strictness.** The spec's five deviations name
  neither, and such a reply holds nothing but the two fields.
- **An answer line with nothing after its label counts as `answer_missing`.**
- **`bad_row_name` means an empty row name only.** An unbalanced bracket in a row name cannot
  be told apart from a missing closing bracket, so it is `syntax` or `wrong_arity`.
- **`run_reply` lives in `dsl/outcome.py`** and is exported from the package, so
  `from qlora_finetuning.dsl import run_reply` is as the spec shows.
- **The executor also checks a program built by hand** (a bad reference, an unknown
  operation), so it cannot be made to misbehave by skipping the parser.

The first three change a decision and are written back into the spec (D26, D7, D9).

## Still open, for later versions

- Rounding, tolerance, reading the answer line as a number, the four metrics: v2.02.
- The gold self-check over all 8,281 examples needs the test rows' programs, which only code
  inside `qlora_finetuning/data/` may read: v2.02 decides how.
- The repeated-row rule rests on the published evaluator, not on a measurement.
- Two labels on one line (`PROGRAM: ... ANSWER: ...`) are read as one program and fail as
  `syntax`. If a baseline model does this often, v3.01 or v4.01 will show it.
