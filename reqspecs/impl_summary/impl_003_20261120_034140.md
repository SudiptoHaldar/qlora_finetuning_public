## Summary

- **Failure categories** (`qlora_finetuning/evaluation/failures.py`). `classify` gives a
  reply `right` or the first of thirteen categories that fits, from the stored outcome, the
  stop reason, and the gold program: cut off, no program, bad program, not executable, kind,
  more or fewer steps, another operation, other numbers, arguments reversed, and, for the
  gold program itself, scale or sign. `run_failures` and `count_failures` work on any arm's
  stored run. Nothing is judged by reading.
- **The error analysis** (`local_qlora/analysis.py`, `scripts/qlora_analyze.py`). From the
  runs the selection was made from: the categories of the selected checkpoint beside the
  untuned model, the categories at every checkpoint, the trend of the last three, the
  failures by gold program length, operation, company, and prompt length, the examples no
  checkpoint got right, and a finding (T1 to T5, or none). The committed report holds
  counts and example ids; `--show` prints replies to the terminal only.
- **The registered change** (`local_qlora/iteration.py`, `iteration_record.py`,
  `scripts/qlora_iterate.py`). `propose` checks that arm A1 missed, that it is analysed,
  that `config/training.yaml` differs from the first run in exactly one allowed variable,
  that no second run has been made, and that nothing the arms share has changed; then it
  writes `reports/local_qlora/iteration.json`. `status` says where the iteration stands
  and checks that the config is the selected run's.
- **Launch check J10** (`local_qlora/sagemaker.py`). Once a checkpoint is selected, a full
  training run from its start needs the registered change, the first job's workspace, and
  that no second run has completed. A first run, a resume, and the other tasks pass.
- **Selecting across two runs** (`local_qlora/selection.py`). The reading of a run's scored
  checkpoints is now `gather_scored`, shared with the analysis. Given the registered second
  run, the selection compares its best checkpoint with the selected one by the same rule
  (a tie keeps the first), writes a schema 2 record that names the winner and lists both
  runs, keeps the first record, notes whether the gap is within noise, and completes the
  iteration record.

## Issues resolved

- **Two stand-in runs shared their weights.** The test engine writes the same bytes at a
  step in every run, so the second run's checkpoints had the first run's hashes and the
  score task, correctly, reused the first run's results. The test world now gives a second
  run weights of its own. Real runs cannot collide this way; the behavior it exposed (an
  adapter is known by its hash, whatever run it sits in) is the intended one.
- **A stand-in job name collided with the launcher's** in one test, which then looked at
  the wrong entry of the job record. The test looks the job up by name.
- **Splitting `select_checkpoint`** left v3.04's selection tests passing unchanged, which
  is what guarded the refactor.
- **One sentence in `gotchas.md`** claimed that two of the four reversed replies had a
  negated value. That was not measured; it now says what was: 4 of 14 failures were
  reversed arguments, and 2 of the 14 wrong values were the negative of gold.
