## Summary

**The tuned predictors.** `python -m scripts.evaluate --predictor nova-lite-tuned` (or
`nova-pro-tuned`) scores a fine-tuned model with the runner that scored its baseline. The
predictor is the existing `FrontierPredictor`; only the `modelId` differs, and it is the
ARN of the deployment that the tuning record names for the model's latest attempt. Before a
run starts, and before anything is billed, it refuses unless the job completed, the
deployment is recorded as Active, the model was tuned on the export the gate record names
for today's prompt and split, and Bedrock, asked once, confirms the deployment is Active.
Each refusal names the command to run.

**Called under one id, billed under another.** A tuned run's `model_id` is the deployment's
ARN, so a resume against another deployment is refused by the existing rule. Its tokens are
recorded in the ledger under the base model's id (`usage_model_id`), which is what Bedrock
bills it as and what `config/pricing.yaml` can price. Without that, the v4.03 cap check
would have counted tuned inference as nothing.

**The report.** `python -m scripts.nova_tuned --runs <B1> --baselines <B0>` pairs each tuned
run with the baseline run of its model and split, runs six checks, and writes
`reports/frontier/nova_tuned_report.md` and `.json`: both scores and the difference in
points, the questions tuning fixed and broke with an exact sign test, the cost per example
and per correct answer, the cost of the tuning job beside them, and a verdict per model
from dev only. It calls no AWS service.

**The owner's three decisions** (2026-11-18) are built in: missed means less than 10 points
above the model's own baseline on dev execution accuracy, or format validity under 98%;
quick-dev and dev are both scored; the deployments are kept. The thresholds are in
`config/frontier.yaml`. A missed verdict makes v4.05 eligible and starts nothing.

## Issues resolved

- **An ARN in the ledger would have hidden tuned inference from the cap check.** Found
  while reading `committed_path_b`, which counts a record whose model has no price as
  nothing. Usage is recorded under the base model's id instead, and a test adds a tuned run
  and checks that the committed amount rises by exactly its cost.
- **A test of mine expected one failed check where two are right.** Dropping a dev baseline
  leaves a model without a dev pair, so V6 fails with V2. The test now drops a quick-dev
  baseline.
- **An empty list in the config is reported as a missing key** by the config loader, before
  my own message could be. The test case uses a list with a wrong entry.
- **A patch script written through the shell lost its quotes**, as in v4.03. Written as a
  file instead.
- **Seven lint findings** (long lines, a variable named `l`), fixed.
